# Supply Chain — Knowing What You Shipped And Where It Came From

Scope: artifacts, their identity, their contents, their provenance, and the policy for the vulnerabilities inside them. Building the image is `docker`; running it is `deploys.md`.

**Before answering "what is running" or "is this CVE relevant"**, read `## Delivery Setup` in `~/Clawic/data/devops/memory.md` (registry, artifact identity scheme, base images), `## Services` for what each service ships, and `releases/<year>.md` for what is actually deployed in each environment.

## Artifact Identity

- Every build produces one immutable identity — a content digest, plus a human tag from `version_scheme` (`git-sha` by default). Movable tags (`latest`, `prod`) are pointers you retarget, never the thing you deploy by.
- **Promotion retags the same digest**; it never rebuilds. Rebuilding "the same commit" produces a different artifact whenever a base image, a transitive dependency, or a timestamp moved.
- Reproducible builds are the ideal and rarely free. The practical substitute is: build once, record the digest, and never build the same version twice.
- Record the identity at deploy (`releases/<year>.md`) — it is the rollback key, the CVE-blast-radius key, and the answer to "who shipped this".

## Registry Hygiene

| Problem | Consequence | Policy |
|---|---|---|
| No retention rule on PR/branch tags | Storage grows forever; nobody owns the bill | Delete PR tags after a stated window; keep release tags |
| Garbage collection deletes the digest you would roll back to | The rollback becomes a rebuild | Protect digests referenced by any environment for at least the rollback window |
| Anonymous pulls from a public registry in CI | Rate limits hit at random times behind a shared NAT | Authenticate, or mirror the handful of base images you use |
| One registry namespace for everything | A compromised push credential reaches every service | Namespace per team or per trust level, credentials scoped to it |
| Mutable release tags | "It worked yesterday" cannot be reproduced | Immutable tags where the registry supports them |

## Provenance And Signing

Three separable claims — implement in this order, each one useful alone:

1. **Provenance**: this artifact was built by this pipeline, from this source revision, with these inputs. Generated by the build system as an attestation. It answers "did this come from our pipeline at all", which is the question a compromised laptop makes urgent.
2. **Signature**: someone (a pipeline identity, not a person's laptop key) attests to the digest. Keyless signing tied to the pipeline's workload identity avoids a long-lived private key entirely (`secrets.md`).
3. **Verification at admission**: the deploy target refuses unsigned or unattested artifacts. Without this step, 1 and 2 are metadata nobody enforces.

Verification must fail closed in production and can warn-only in lower environments while it is being adopted. Write the adoption decision, including which environments enforce, as an artifact — this is exactly the policy that gets silently disabled during an incident and never re-enabled.

## SBOM

A machine-readable inventory of what is inside an artifact, produced at build time and stored with it.

- Its value is *speed of answer*: when a widely used library gets a critical advisory, the question is "which of our 40 services ship it, in which version" — SBOMs answer in minutes, manual archaeology takes days.
- Generate at build (when the dependency resolution is known) and attach to the artifact, not to the git tag: the artifact is what runs.
- Include OS packages and application dependencies. An SBOM covering only your language's lockfile misses the base image, which is where most CVE noise originates.
- An SBOM nobody can query is a compliance artifact, not a tool. Decide where they are stored and how you search across them before generating thousands.

## Vulnerability Triage

Scanners report by CVSS; exploitability in *your* context is what should drive work. Triage on three questions:

1. **Reachable?** Is the vulnerable code path used by this service at all? Most CVEs in a base image are in packages the service never calls.
2. **Exposed?** Is the affected surface reachable from untrusted input, or only from an internal, authenticated path?
3. **Fixable?** Is there a patched version, and does upgrading it break anything?

Write an SLA and stick to it — the shape matters more than the exact numbers, and a written policy is what stops the queue from becoming permanent noise. A common shape: critical and reachable within days, high within weeks, everything else on the regular dependency-update cadence. Record the chosen numbers as `cve_sla` under the `compliance` area of `config.yaml` (SKILL.md, Configuration), since `compliance_regime` may dictate them.

Practical rules:

- **Scan at build and again in the registry on a cadence.** CVEs are published after the build; an image approved in March rots where it sits. The rebuild-and-rescan cadence is a row in `## Due`.
- Rebuilding on the current base image fixes the majority of OS-package findings with no code change; do that before triaging individual packages.
- Suppressions expire. A permanent ignore entry with no date and no owner is how a real vulnerability lives for two years.
- Distinguish "scanner noise" from "we accepted the risk" in the record; only the second one is a decision, and it needs a name attached.

## Dependency Updates

- Automate the proposal, gate the merge. An update bot with auto-merge on green means your test suite is the only thing standing between a compromised package and production.
- Batch patch updates weekly; review minors; treat majors as planned work with their own release.
- Lockfiles are mandatory and committed; without them the build is not reproducible and "it worked yesterday" is unanswerable.
- Pin by digest or checksum where the ecosystem supports it, especially for base images and build-time tooling.
- Watch for the ecosystem-specific attack shapes: typosquatted names, a maintainer handover on a widely used small package, and install scripts that run at dependency-resolution time (before any test does).

## Third-Party Build Steps

Every action, plugin, or container in the pipeline executes with the pipeline's privileges.

- Pin by commit SHA, not tag (`secrets.md`).
- Prefer first-party or widely audited steps for anything that touches credentials; a two-line convenience wrapper around a CLI is worth writing yourself.
- Review what a step can see: the checkout, the environment, the cache, the token. A step that only needs to post a comment should not run in the job that holds deploy credentials.
- Mirror or vendor the critical few, so an upstream deletion or repointing does not stop your releases.

**Write in the same turn**: registry, artifact identity scheme, and the base images in use go in `## Delivery Setup` of `~/Clawic/data/devops/memory.md`; the rebuild, rescan, and dependency-refresh cadences with their last run go in `## Due`; a signing/verification or CVE-SLA decision, with what it rejected, becomes `artifacts/<kebab-name>.md` with its `## Boxes` line; an exploited or exposed vulnerability becomes a row in `incidents/<year>.md` (`memory-template.md`). Registry and signing credentials are pointers, never values.
